# Personal Life OS — 威胁模型

> 版本：V0.8-01 | 面向个人使用的 Django 单体应用。

---

## 威胁总览

| # | 威胁 | 影响 | 当前状态 | 建议 |
|---|------|------|----------|------|
| 1 | 账号被盗 | 数据泄露、伪造记录 | ⚠ 部分缓解 | 强化密码策略 + 2FA |
| 2 | 越权访问 | 查看/修改他人数据 | ✅ 已缓解 | 持续审计 |
| 3 | API Key 泄露 | AI 额度被盗刷 | ✅ 已缓解 | .env + .gitignore |
| 4 | 数据库泄露 | 全部数据暴露 | ⚠ 部分缓解 | 加密备份 + 最小权限 |
| 5 | AI 数据外发 | 敏感信息发送到 DeepSeek | ✅ 已缓解 | 敏感检测 + 本地规则 |
| 6 | 备份泄露 | 历史数据暴露 | ❌ 未处理 | 加密备份 |
| 7 | 恶意请求 | 暴力破解、SQL注入、XSS | ⚠ 部分缓解 | 限流 + CSP |
| 8 | 通知误发 | 骚扰、信息泄露 | ✅ 已缓解 | 站内通知兜底 |
| 9 | 数据误删 | 记录丢失 | ✅ 已缓解 | 软删除 + 审计日志 |

---

## 1. 账号被盗

**威胁描述**：攻击者获取用户名密码 → 登录系统 → 查看/删除/篡改个人数据。

**当前防护**：
- Django 密码哈希（PBKDF2）
- CSRF 保护
- 会话管理（`django.contrib.sessions`）

**残余风险**：
- 无密码复杂度要求（`AUTH_PASSWORD_VALIDATORS = []`）
- 无登录失败限流
- 无 2FA

**建议**：
- 启用 Django 密码校验器
- 添加登录失败限流（django-ratelimit 或自定义中间件）
- 考虑 TOTP 两步验证

---

## 2. 越权访问

**威胁描述**：用户 A 通过修改 URL 参数访问用户 B 的记录。

**当前防护**：
- 所有查询通过 `request.user` 过滤
- `_check_owner()` 权限守卫 → 404
- 数据隔离测试覆盖（`DataIsolationTests`）

**残余风险**：
- Admin 后台无限制（`is_superuser` 可看所有数据）
- 批量接口未做每行权限检查

**建议**：
- Admin 仅开发环境启用
- 生产环境 `DJANGO_DEBUG=False`

---

## 3. API Key 泄露

**威胁描述**：DeepSeek API Key 泄露 → 第三方盗刷 API 额度。

**当前防护**：
- API Key 仅存 `.env`，不在代码中
- `.gitignore` 排除 `.env`
- `AuditLog` 模型无 API Key 字段
- `ConversationLog` 不记录 Key
- `.env.example` 提供模板

**残余风险**：
- 服务器被入侵时 `.env` 可读
- 日志中可能意外记录 Key

**建议**：
- 定期轮换 Key
- 设置 API 用量告警

---

## 4. 数据库泄露

**威胁描述**：`db.sqlite3` 文件被直接读取。

**当前防护**：
- SQLite 文件在 `.gitignore`
- 生产环境计划使用 MySQL

**残余风险**：
- SQLite 无加密
- 无传输加密（开发环境 HTTP）

**建议**：
- 生产环境：MySQL + 磁盘加密
- HTTPS 传输加密
- 数据库账号最小权限

---

## 5. AI 数据外发

**威胁描述**：用户输入包含敏感信息（身份证号、密码等）→ 发送到 AI API。

**当前防护**：
- `_check_sensitive()` 检测敏感内容
- 命中敏感内容 → 返回本地解析，不调用 AI
- FakeProvider 兜底
- 用户可关闭 AI（`ai_parsing_enabled`）
- 隐私说明页面（`/common/privacy/`）

**残余风险**：
- 敏感检测基于关键词，可绕过
- DeepSeek API 端数据留存策略未知

**建议**：
- 用户可选择不开启 AI
- 生产环境与 API 供应商确认数据留存政策

---

## 6. 备份泄露

**威胁描述**：数据库备份文件被未授权访问。

**当前防护**：
- 无自动备份

**残余风险**：
- 备份尚未实现

**建议**（V0.8-03 实现）：
- 备份文件加密
- 备份存储于独立位置
- 定期测试恢复流程

---

## 7. 恶意请求

**威胁描述**：
- 暴力破解：反复尝试登录
- SQL 注入：恶意构造查询参数
- XSS：注入脚本到页面
- CSRF：跨站请求伪造

**当前防护**：
- Django ORM 防 SQL 注入
- CSRF 中间件
- Django 模板自动转义 HTML
- `@login_required` 保护敏感视图

**残余风险**：
- 无限速登录
- `ALLOWED_HOSTS` 开发环境为 `*`
- 无 CSP 头

**建议**：
- 添加登录限流
- 生产环境设置正确的 `ALLOWED_HOSTS`
- 添加 Content-Security-Policy 头
- 启用 `SECURE_HSTS_SECONDS` / `SECURE_SSL_REDIRECT`

---

## 8. 通知误发

**威胁描述**：重复通知、错误通知、通知发给错误用户。

**当前防护**：
- `idempotency_key` 唯一键防重复
- `scan_reminders` 每日扫描，不重复生成
- 站内通知兜底（`NotificationLog`）
- 邮件通知可关闭（`email_notifications`）
- 邮件不包含金额/分类细节

**残余风险**：
- Web Push 推送失败时可能遗漏

**建议**：
- 站内通知始终保留
- Push/邮件作为附加通道

---

## 9. 数据误删

**威胁描述**：用户误操作删除记录。

**当前防护**：
- `is_deleted` + `deleted_at` 软删除
- `AuditLog` 记录所有修改/删除操作
- 分类停用前检查引用（`refs > 0` 阻止）
- `data_check` 命令可检测异常
- 部分操作有确认页面

**残余风险**：
- 软删除记录最终可被物理删除
- 无时间窗口内的自动恢复

**建议**：
- 保留软删除记录至少 30 天
- 定期备份数据库
