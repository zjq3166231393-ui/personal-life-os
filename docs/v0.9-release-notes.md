## 版本目标

V0.9 是**功能完整度与体验**的双重跃迁：

1. 补齐主流记账 App 的核心能力（游戏化激励、批量操作、四象限、OCR、语音记账、记账提醒、报表同比环比、储蓄目标、信封预算、净值趋势、现金流预测、全局快捷键）；
2. 以 **taste-skill 重设计**统一全站视觉语言（指挥中心首页、主题色图标瓦片、统一 1.5px 图标库、品牌 Hero 令牌化），再经 **impeccable 审计与打磨**达到生产级质量；
3. **差距清单落地阶段**补齐与头部产品的差距——P0 级（周期性账单自动入账、支付宝/微信 CSV 导入、凭证附件、回收站/撤销）与 P1 级（年度账单、规则自动分类、N+1 查询消除、多币种、移动端滑动手势），全部本地提交并通过完整测试套件。

## 稳定性修复：登录后首页崩溃

### 症状

登录后跳转首页即 500，`/expenses/`、`/countdowns/` 同报，表现为「登不进去、全是报错代码」。

### 根因

**不是代码坏了，是开发库没跟上代码。** `db.sqlite3` 落后 4 个迁移（`0035`~`0038`），
任何读取新字段的查询都会抛 `OperationalError: no such column`，而登录后默认跳转首页 → 首页崩。

| 页面 | 报错字段 |
|------|---------|
| `/`（首页，登录后跳转目标） | `life_recurringexpense.auto_post` |
| `/expenses/` | `life_expense.currency` |
| `/countdowns/` | `life_account.currency` |

> ⚠️ **关键教训**：Django 测试跑在**独立测试库**上，所以 668 项全绿**完全发现不了**
> 开发库漂移。这也是下面「迁移漂移防护」存在的原因。

### 修复项

| # | 修复 | 状态 |
|---|------|------|
| 1 | 备份开发库 → `backups/db.sqlite3.pre-migrate-20260831.bak`，应用 `0035`~`0038` | ✅ |
| 2 | 回填 102 条历史数据的 `amount_base`（迁移只加字段、未回填） | ✅ NULL 归零 |
| 3 | 修掉 `/common/notifications/` 的真实崩溃：先 `[:50]` 切片再 `.filter()` → `TypeError` | ✅ |
| 4 | 全库扫描「切片后再过滤」反模式 | ✅ 仅此一处 |
| 5 | 新增**迁移漂移防护**，从机制上杜绝复发 | ✅ |
| 6 | 全站 90 个 URL 冒烟 + 真实 HTTP 登录链路验证 | ✅ 真实 bug 归零 |

### 迁移漂移防护（新增）

- 模块：`life/migration_guard.py` —— `pending_migrations()` / `auto_migrate_if_needed()`
- 接入：`manage.py` 在执行 `runserver` 前调用；**仅 `DEBUG` 模式介入**，生产由 gunicorn 启动、不受影响
- 行为：库已同步时**完全静默**；检测到漂移则打印醒目横幅并自动执行 `migrate`
- 关闭自动修复：`python manage.py runserver --no-auto-migrate`（只提示、不修复）
- 尊重命令行 `--settings=xxx`，避免守卫连到错误的库
- 任何异常都不会阻断服务器启动（整体包在 try/except 中）
- 测试：`tests_migration_guard.py` 9 项；`common/tests.py` 补 4 项通知页回归

> 说明：Django 自带的 `You have N unapplied migration(s)` 提示在启动日志里一闪而过，
> 极易被忽略——本次故障正是因此潜伏。该防护把它升级为「醒目提示 + 自动修复」。

### 验证方式

| 验证 | 结果 |
|------|------|
| 真实 HTTP 登录（带 CSRF token） | 正确密码 → 302 → `/` → 200 |
| 错误密码 / 不存在用户 | 200，回显「用户名或密码不正确，请重试。」 |
| 全站 90 个 URL 爬取 | 71 成功 / 17 个 405（POST-only，预期）/ **真实失败 0** |
| 隔离临时库人为制造 25 个漂移 | 守卫检测 → 自动应用 → 复检归零 → 服务正常启动 |

- 验证：临时冒烟测试确认首页「更多功能」宫格与 13 个功能页均正常渲染（已删除临时文件）。

## 已知限制

| 类别 | 限制 | 计划 |
|------|------|------|
| OCR | 本机无 Tesseract / 未装 pytesseract，实际识别需装二进制或配云服务 | 按需启用 |
| 语音 | 依赖浏览器 Web Speech API（Chrome / Edge），不支持时无入口 | 渐进增强 |
| 多币种 | ✅ 已落地增量 MVP（CNY 锚定 + 手动汇率）；暂未接外部汇率 API，统计口径仍为单币种 `amount` | 后续按需接入实时汇率 |
| 银行同步 / 投资 / 多人协同 | 不计划 | 与自托管 / 数据自有定位冲突 |
| CSP 头 | 未配置 | 生产部署审查 |
| 推送通知 | Web Push 需 HTTPS + VAPID | 生产部署时配置 |

## 部署提示

- 经 `Dockerfile`（gunicorn -w1）由 **Railway 自动部署**；推送 `release-v0.9.0` 即触发
- 必须环境变量：`DJANGO_DEBUG=false`、`DJANGO_ALLOWED_HOSTS`（具体域名，禁 `*`）、`DJANGO_ENVIRONMENT=production`
- `collectstatic` 已接 whitenoise；注意 Dockerfile 中 `... || true` 会**静默吞掉收集失败**——上线前确认构建期能成功 `collectstatic`，否则上线后 CSS/JS 全 404
- ⚠️ **部署后必须执行一次 `python manage.py migrate`**：生产走 gunicorn，本项目的本地迁移漂移防护
  （见「稳定性修复」）**不会**在生产生效。忘记 migrate 会导致线上页面抛 `no such column`，
  症状与本地故障完全一致（登录后首页即崩）。建议把 migrate 接进 Railway 的 Deploy 阶段。
